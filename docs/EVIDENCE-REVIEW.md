# 证据评审的落地记录

> 本轮改动的正本。来源是一份外部设计评审（《FocusFlow 设计评审：理念基础与改进建议》），
> 它基于时间管理 / 拖延领域的文献梳理，给了 6 条建议和 5 个「留给作者决定」的开放问题。
>
> 那份评审有一句话决定了这份文档的写法：**「理由比建议本身重要，遇到我没写到的情况时，
> 请按理由推导，而不是按建议照做。」** 所以下面每条都记「按原样做 / 按理由改了做法 / 没做」，
> 改了的一定写清楚是哪条理由把它推到了别处。

---

## 0. 一句话背景：评审看的是改造前的代码

评审的基线是 **10 档优先级（A–H + N + S）、F 无限灵感池、周六复盘、101 个单元测试**。
在它写成之后、落地之前，仓库已经完成了 sleek 互通改造（见 `SLEEK-INTEROP.md`）：
档位降到 7、F/N/S 删除、周期改成周一起、候选池搬到共享 `todo.txt`。

**这不是巧合，是同一个诊断的两次到达。** 评审的建议 6（优先级收敛）和 sleek 改造是从
两个方向指向同一件事：分类摩擦要降，而降的办法是把「还没进入本单元」这件事从优先级里
拿出去。sleek 改造把它放进了一个文本文件，评审只是没看到这一步已经发生。

后果是：**建议 6 大部分已经完成**，而建议 2、3 的实现位置需要按新架构重新推导（见 §2.3）。

## 1. 三件评审不知道的事实

落地前先把代码摸了一遍，有三处和评审的描述不符，都影响做法：

### 1.1 streak 是死代码，不是待删的功能

`currentStreak` / `longestStreak` 在 `types/index.ts` 里声明、在 store 里初始化为 0，
**然后没有任何一行代码给它们加过 1**。所以：

- 「维持 3 天连续」徽章的条件是 `s.currentStreak >= 3`，**永远不成立**
- `perfectDays` 同样从未被写入 → 「可持续工作者」徽章同样永远解锁不了
- `earlyBirdCount` / `nightOwlCount` 有写入，但没有任何徽章或 UI 读它们

**六个徽章里有两个从上线那天起就是坏的。** 所以「删 streak」在这里不是一个取舍，
是修 bug；评审给的理由（漏一天对习惯自动化不可见，而 streak 把它变成灾难）依然成立，
只是它顺便说明了为什么删起来零成本。

### 1.2 `FreshStart.svelte` 已经没有任何引用

建议 3 说「把 `FreshStart` 里已有的『>30 天且非 A 非重复』筛选逻辑提升为常驻组件」。
实际情况是这个组件（3.4K）**没有任何地方 import 它**，是死文件。所以没有东西可提升，
新组件是重写的，旧文件直接删除。

### 1.3 建议 2 和建议 5 对「估计系数」的定义互相矛盾

- 建议 2：`estimationFactor(reviews) = median(实际 / 计划)`，从 `UnitReview.stats` 推导
- 建议 5：「`pomodoros.estimated` 保留并**用于估计系数计算**」

这两个不是同一个量。`UnitReview.stats` 存的是 planned / completed 的**分优先级计数**，
它们的比值是**完成率**——「我计划做 8 件，做完了 5 件」。而参考类预测要的是**校准度**
——「我以为要 2 个番茄，实际花了 3 个」。

**取建议 5 的定义。** 完成率对「我是不是高估了自己的产能」有信息，但它会被
「少承诺」直接改善，而校准度不会：把估计报高会让系数掉到 1 以下，一样难看，
而且对完成任何事都没有帮助。

## 2. 逐条落地

### 建议 1 · 删 streak，游戏化默认关闭 — ✅ 做了，之后作者决定**彻底删除**

- `currentStreak` / `longestStreak` / `perfectDays` / `earlyBirdCount` /
  `nightOwlCount` 全部从 `GamificationStats` 删除
- 两个永远解锁不了的徽章（`consistency_is_key`、`sustainable_worker`）删除
- 先落成 `settings.gamificationEnabled`，**新装和已有安装都默认 `false`**；
  关闭时**不计分**，而不是「计分但不显示」（后者留着一个在跑的分数，任何人打开开关
  都会看到一次跳变，那本身就是一次推动）
- **然后作者选了彻底删除。** `gamification.svelte.ts`、`BadgesModal.svelte`、
  `Confetti.svelte`、XP / 等级 / 徽章、`settings.gamificationEnabled`、
  ui store 的 `isBadgesOpen`、两个语言文件里的相关 key，全部删掉，净 −992 行、
  bundle 小 12 kB。`gamificationEnabled` 进 `REMOVED_SETTINGS`，`gamification`
  数据块因为存盘路径是逐字段构造而非展开，下一次普通保存就会自然脱落。

**一个实现上的坑，值得记下来。** 清理退役字段的逻辑一开始写在游戏化 store 的
`load()` / `getData()` 里。但那个 store **只通过自己的 persist 回调写盘**，而回调只在
计分时触发——默认关闭之后就是「永远不触发」。于是那些废弃 key 会在 `active.json` 里
躺到天荒地老。清理必须放在 `storage.ts` 的加载路径上（`migrateGamification()`，
就在 `migrateSettings()` 旁边），这样下一次任何普通保存都会把它带出去。

> 评审给的折中方案「XP 只对 A/S 计分」没有采用。它确实能让计分不再奖励刷小任务，
> 但保留了「完成量即价值」这个暗示，而那正是和配额冲突的东西。默认关闭是更干净的答案，
> 而且不排除以后彻底删掉——留在开关后面的代码删起来是零风险的。

### 建议 2 · 三个流动指标 — ✅ 做了，位置按新架构推导

新增 `src/lib/utils/flowMetrics.ts`（Node-safe，无 Svelte / Tauri / i18n 依赖，
CLI 和测试直接 import），21 个单元测试：

| 函数 | 测什么 |
|---|---|
| `ageDistribution` | 未完成项的年龄分布：p50 / p90 / 最老的那一条 |
| `cycleTimeMedian` | 创建 → 完成的中位天数，取最近 20 条 |
| `estimationFactor` | 实际番茄 / 估计番茄 的中位数，可按档位限定参考类 |
| `commitmentCount` | 当前承诺数（配额可见化） |
| `samplesUntilReady` | 还差几条完成记录才能给出可信中位数 |

主界面 `CompletionSparkline`（完成率趋势，存量指标）替换为 `FlowStrip`：
**在办 N/15 · 最老 N 天 · 周期 N 天 · 估计 ×N**。

**三个实现决定：**

1. **样本不足返回 `null`，不返回数字。** 阈值 5 条。三条数据的中位数是「戴着小数点的噪声」，
   显示出来会被当成结论。空状态显示「还需 N 个」。
2. **日期一律走本地日历日**：两端归零到本地午夜再相减取整。所以昨晚 23:00 建的任务今早看是
   1 天，不是 0 天；夏令时那个 23 小时的日子也还是 1 天。（`toISOString()` 在这个项目里
   是禁用的，理由见 `CLAUDE.md` 的 Testing 一节。）
3. **周期时间排除已取消（H）任务。** 取消是一个正当结果，但它不是交付。算进去的话，
   放弃的活儿越多这个数越好看——那就把它变成了可以表演的指标，正是要避免的东西。

**一处对评审的偏离：`estimationFactor` 跳过番茄完成数为 0 的任务。** 0 意味着
「没用计时器」，不意味着「没花力气」。算进去会把系数拖向 0，然后告诉用户
「你系统性高估一切」——一个精确的错误结论。

### 建议 3 · 年龄分布常驻，最老项置顶 — ✅ 做了，但**测的范围**变了

新增 `OldestOpenRow.svelte`，挂在 `App.svelte` 的视图切换器**外面**——切标签页
关不掉它，这是这个数字全部价值所在。

**范围的偏离，这是本轮最重要的一处推导。** 评审写的时候，长期堆积的东西在 F 灵感池里，
所以「最老的未完成项」自然覆盖全部积压。sleek 改造之后，积压搬进了共享 `todo.txt`。
那要不要把候选池也纳入年龄统计？

**不要。** 理由来自评审自己：它认可 F 作为无限池是对的，因为**「它是库存，不是承诺」**。
库存本来就该躺着；把库存的年龄当成债务显示出来，是在因为用户保留了一个待办清单而惩罚他，
而保留清单恰恰是清单存在的意义。所以这个数字只测**已经承诺的活儿**——单元里的任务。

但年龄的**起点**仍然来自候选池：从 todo.txt 拉取的任务，`createdAt` 取的是那一行自己的
创建日期（`taskFromTodoTxt` 已经这么做了）。所以拉取**不重置时钟**——一行在文件里躺了
七周，拉进来还是七周。行上没有创建日期时才从拉取时刻起算，这时数字是个**下界**：
少报债务，不凭空制造债务，这是该错的方向。

**两个动作，两条硬规则：**

- **「做掉」不是改优先级。** 它要求填一个情境线索，然后把任务挪进当前单元。
  一个在硬性 15 条上限的系统里躺了 47 天的任务，不是在等产能——它在被回避，
  而回避跟踪的是任务厌恶度，厌恶来自模糊和能力威胁。所以有效的动作是**降低启动阈值**，
  不是提高优先级（提高优先级只会让同一个模糊的东西更显眼）。
- **「杀掉」和「做掉」等权，无确认弹窗、无安慰文案。** 自责不是纠正机制，是回避的燃料；
  而如果删除看起来像失败，就没有人会删任何东西，队列永远清不掉。

阈值 **14 天**才长出这两个按钮。一个单元 2 天，14 天意味着这条任务被连续带过了 7 个单元。
低于这个数只显示年龄不显示按钮——3 天的任务就只是一个任务，不值得打断。

### 建议 4 · `trigger` 字段（if-then） — ✅ 做了

`Task.trigger?: string | null`，自由文本，永不必填、不填也不提示。

- 输入语法 `when:<线索>`，**吃到行尾**（所以要放最后），在所有其他 marker 之前解析
- 编辑弹窗里是一整行的独立字段，在日期栅格**上方**
- 卡片上渲染在正文**上方**：它是任务开始的条件，不是关于任务的元数据，
  要先读到它才起作用。视觉上和截止日明确区分。

**存哪里：只存在 FocusFlow，不写回 todo.txt。** 两个理由，第二个更重要：

1. todo.txt 的扩展值不能含空格（`[^\s:]+:[^\s:]+`），而「坐下打开电脑后」是个短语。
   没有诚实的往返方式。
2. 更根本的是**它本来就属于这一层**。候选池存的是「可以做什么」，FocusFlow 存的是
   「未来两天承诺要做什么、以及我打算怎么开始」。if-then 是一个启动机制，
   它是承诺的属性，不是积压条目的属性。

**一个被浏览器实测抓到的 bug**（单元测试没覆盖）：`QuickAddRow` 会把所在列的优先级
以 `${text} !${priority}` 追加到输入末尾（靠「解析器取第一个 `!X`」保证用户自己打的
优先级仍然胜出）。而 `when:` 吃到行尾，就把这个 `!C` 吞进了线索里，结果 trigger 存成
`"午饭回来倒完水坐下后 !C"` 且档位丢失。修法：**「吃到行尾」指的是用户那一行的行尾**
——线索末尾的 `!X` / 【X】token 交还给正文，再走优先级解析。

### 建议 5 · 番茄周期可配置、计数不上主界面 — ✅ 做了

- `settings.pomodoroWorkByPriority`：A/B 默认 50 分钟，C/D/E 默认 25，五档都可改
- `pomodoros.completed` 不出现在主界面任何位置（`FlowStrip` 里没有累计番茄数）
- 但它**参与估计系数计算**——那是校准，不是产量
- `ImmersivePomodoro` 保留：全屏无干扰是**情境控制**，是软件在这一层唯一有对照证据的动作

25 这个数字没有实证依据（来自发明者的厨房计时器），而对照研究显示 12–3 和 24–6 差别不大
——起作用的是「有外部结构」本身。所以功能保留，那个数字的权威性去掉。

### 建议 6 · 优先级档位收敛 — ✅ 全部做完

第一半随 sleek 改造：

- A–E 保留，配额不动
- F 与 N 删除。它们表达的都是「还没进入本单元」，那是共享文件里一行的状态
- S 变成 `+project`（`settings.focusProject`），子任务变成带同一标签的普通任务

第二半在作者拍板后做掉了（数据版本 5.0 → 6.0）：

```ts
type Priority   = 'A' | 'B' | 'C' | 'D' | 'E';          // 五个档位，没别的
type TaskStatus = 'open' | 'completed' | 'cancelled';   // 发生了什么，独立一轴
```

**G/H 从来就不是档位**，它们是任务*发生了什么*，和「有多重要」正交。把它们塞在
同一个枚举里，直接后果是**完成会覆盖优先级**——于是必须再开一个
`originalPriority` 把档位存起来，每个想知道「这原来是什么级别的活儿」的地方都得
读回来；而每个接受 `Priority` 的函数都要处理两个它什么也做不了的值。

两个补偿字段一起没了：

- `originalPriority`：档位现在能穿过完成，没有东西需要放回去
- `completed` 布尔：它是 `status === 'completed'` 的第二种可独立设置的写法，
  而 CLI 和 app 对怎么设它已经出现分歧了

四个 helper 也没了——`isActivePriority` / `isOperablePriority` /
`isCountedPriority` / `isHiddenPriority`，它们唯一的工作是问「这到底是不是一个
真档位」。这个问题不再需要问，换成 `isOpen(task)` / `isFinished(task)`，
问的是状态，那才是真正要问的东西。

**变简单而不只是搬家的几处：**

- `uncompleteTask` 原来是「查 originalPriority，查不到落默认档」，现在就是翻个状态
- `recentlyCompletedTasksByPriority` 不再需要解析档位——完成的任务显示在它被完成的
  那一栏，因为它压根没离开过
- `todotxt`：sleek 完成行上的 `pri:` **就是**档位，两边直接对上
- 复盘和周期完成率现在把取消的任务从分子分母**两边**都排除，而不是当成没做完。
  放弃是对计划做的决定，把它记成失败正是让人不敢清队列的原因

**迁移 `migrateV6.ts`**（Node-safe，16 个测试）**无条件运行**，因为它是构造性
幂等的——已经带 `status` 的记录原样通过。这样即使文件是别的工具写的、或者是两个
版本之间某个 build 写的，也能落到一个能读的形态。它认三种老写法：`G`/`H` 加
`originalPriority`、活档位上的裸 `completed: true`（老 CLI 写出来的半截记录）、
以及已经带 status 的。认不出的档位夹到默认值，而不是去毒化每一个按它索引的
`Record<Priority, …>`。

**一个类型上的教训**：`migrateV5` 现在声明返回 `V5Task` 而不是 `Task`。把迁移链的
每一步都标成「当前形态」，正是迁移会静默不跑的原因。

## 3. 开放问题的处置

评审第四部分列了 5 个开放问题。其中三个在这个仓库里已经有答案：

- **Q2（各档当初为什么这样设）**：F/N/S 已经删了，问题消解。
- **Q4（CLI 的定位）**：`cli/focusflow.ts` 有 `agent-guide` 子命令，它就是给 agent 用的接口。
  所以流动指标同时暴露在 CLI：`focusflow metrics [--json]`，样本不足时 JSON 里是 `null`
  而不是数字。
- **Q5（多设备 / `createdAt` 可信度）**：本地文件 + 共享 todo.txt，没有多端合并。
  拉取的任务 `createdAt` 取自 todo.txt 行的创建日期，见 §2.3。

另外两个问题提给了作者，两个都拍了板：

### Q1 · 游戏化最终怎么处置？ → **彻底删除**

我实现的是「默认关闭的开关」并推荐保持现状，因为它是「彻底删除」的超集：默认关闭
之后再删代码是零风险的，反过来不成立。作者选了删。这是产品定位问题不是证据问题，
所以是作者的决定；落地见 §2 的建议 1。

### Q3 · G / H 要不要抽成独立的 `status` 字段？ → **现在就做**

我的建议是暂时不做，理由是收益（代码整洁）小于波及面。作者的理由更硬：
**刚做完 5.0 迁移，现在做只需要再来一次数据迁移，以后做要两次。** 这条压过了
我的顾虑，做掉了；落地见 §2 的建议 6。

这里值得记一笔：我给的判断是「`isActivePriority` 这几个 helper 已经把 G/H 隔离
干净了」。真做完之后回头看，这个判断本身就是症状——那几个 helper 存在的唯一理由
就是隔离这两个不该在枚举里的值，**把补丁的存在当成不用修的理由**是绕圈子。

### Q3′ · trigger 要不要配主动通知？

评审把这个也列为开放问题。**我按理由自己定了：不做时间型通知。** 理由是它会
直接踩掉「减少切换」——通知本身是中断源，而 if-then 的机制恰恰是让行动不依赖
当下的注意力被抓住。

但有一个折中位置留着没动：**app 启动**是这个应用唯一真能检测到的情境线索
（「坐下打开电脑」约等于它）。如果以后要做，那是该做的地方——把带线索的任务在
启动时顶上来，而不是在任意时刻弹一条通知。

## 4. 明确没有采纳的东西

| 评审里的说法 | 这里怎么做的 | 为什么 |
|---|---|---|
| 年龄分布覆盖全部积压 | 只覆盖已承诺的任务 | 候选池是库存不是承诺，见 §2.3 |
| 估计系数 = median(实际/计划) 计数比 | = median(实际番茄/估计番茄) | 前者是完成率，会被「少承诺」改善，见 §1.3 |
| 「XP 只对 A/S 计分」的折中 | 默认关闭整个计分 | 折中保留了「完成量即价值」的暗示 |
| 提升 `FreshStart` 的筛选逻辑 | 重写并删除该组件 | 它是死文件，见 §1.2 |
| trigger 用 `@when:` 语法 | 用 `when:` | `@a:b` 在 todo.txt 里会被判成名为 `a:b` 的 **context**，见 `SLEEK-INTEROP.md` |

## 5. 这一轮**没有**声称的东西

评审最后一段值得原样保留在这里，因为它约束了以后所有相关改动怎么写文案：

这些改动的目的不是让 FocusFlow「更高效」。按评审 §1.7，效应量 0.2–0.5 的干预
在个人尺度上无法自测——两周对两周的统计功效约 8%，要 80% 把握每组需要约 175 天
严格交替。所以**任何声称用户能验证「我变高效了」的 UI 文案都是在生产虚假确信**。

能诚实承诺的只有：**不做错事**——不奖励可被表演的行为、不依赖已被证伪的机制、
不掩盖累积的债务、不把结构性超载重新编码成个人纪律问题。

具体到文案规则：

- 三个流动指标**不设目标值**。一旦设了目标，达成它最快的方式就是只开始那些快做完的事。
- 「最老 47 天」这一行**中性陈述，不评判**，「杀掉」和「做掉」等权呈现。
- 不在 UI 里暗示累积效应会指数增长——效率方法在固定产能下改变吞吐量，它不是复利型的。

## 6. 顺带修掉的第三个 bug：冷存储会弹回热存储

补 `storage.ts` 的 IO 测试时发现的，和评审无关，但严重程度高于本轮任何一条建议。

`archiveTasks()` 把完成超过 14 天的任务从 `active.json` 挪进 `archive.json`，
免得热文件无限膨胀。但**两条加载路径都把这个归档当成「老格式数据」**：把里面每一条
都折回活动任务集，然后（localStorage 那边）删掉 key。于是 `cleanupOldTasks` 刚挪
出去的任务，下次启动原样回来，再被归档一次，如此循环。

Tauri 那条路径更糟：折回之后**不删文件**。所以每次启动，整个归档集都会被重新注入
`active.json`，然后 `cleanupOldTasks` 又把它们（连同重复）追加进 `archive.json`
——两个文件都在无界增长，而这是桌面端的主路径。

修法：**加载路径不再读 `archive.json`**。冷存储就该是冷的。行内的 `trash` 数组还是
会折回（那确实是 3.0 之前的老布局），归档不折。

  迁移链、实际写出的形状都在测试之内。Tauri 分支故意不测——它是同一份代码把
  `localStorage` 换成 `invoke()`，stub 它等于测 stub。

  - **本轮第一批**：47 天的任务在常驻行显示年龄和内容；「做掉」存下线索并把任务挪进
